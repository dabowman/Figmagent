# Fix: [TOOL-021] Batch `search_library_components` (+ [TOOL-026] `get_enabled_library_variables`)

**Pattern**: `missing-batch-tool`
**Priority**: P1
**Estimated savings**: ~10–14 calls per component-discovery session (TOOL-021); ~3–5 per token-discovery session (TOOL-026)

## Why now

[TOOL-021] is at **5 recurrences across 3 distinct repos** (sessions 35, 44, 45, 48, 49) with an unchanged spec since session 44. Session 49 made 18 single-`query` calls in four clean runs. [TOOL-026] is at 6 (41, 44, 45, 46, 48, 49) and the tracker records the two as "identical change" — ship together.

Both tools already take exactly one scalar query and return a formatted text block. The change is additive: accept an optional plural param, keep the singular working.

## Changes

### File: `src/figmagent_mcp/tools/libraries.ts`

**1. `search_library_components` (from line 152) — accept `queries`**

Schema — make `query` optional and add `queries`:

```ts
query: z.string().optional().describe(
  "Search term. Matches against component name, description, and containing frame. Use this OR queries."
),
queries: z.array(z.string()).min(1).max(20).optional().describe(
  "Batch form: search several terms in one call against the same fileKey. Returns one labelled result block per term. Prefer this over repeated single-query calls — the file's component list is fetched once and reused across all terms."
),
limit: z.coerce.number().optional().default(10).describe(
  "Maximum results per query. Default 10."
),
```

Handler — hoist the two REST fetches out of the per-query path, then loop:

```ts
async ({ fileKey, query, queries, limit }: any) => {
  const terms: string[] = queries?.length ? queries : query ? [query] : [];
  if (terms.length === 0) {
    return { content: [{ type: "text", text:
      'No search term given. Fix: pass query: "Button" for one term, or queries: ["Button", "Notice"] for several.' }],
      isError: true };
  }
  try {
    // fetched ONCE for the whole batch — this is where the saving is
    const [components, componentSets] = await Promise.all([
      getFileComponents(fileKey),
      getFileComponentSets(fileKey),
    ]);
    const blocks = terms.map((term) =>
      formatSearchResults(term, components, componentSets, limit || 10)
    );
    return { content: [{ type: "text", text: blocks.join("\n\n---\n\n") }] };
  } catch (error) { /* existing catch, unchanged */ }
}
```

Extract the existing scoring/formatting body (the `scored` array through the `parts.join("\n")`) into a module-level `formatSearchResults(query, components, componentSets, maxResults): string` that returns the text for one term, prefixed with `## <query>` so batch output is navigable. The single-query path then produces byte-identical output to today apart from that heading — acceptable, but if strict back-compat is wanted, omit the heading when `terms.length === 1`.

**2. `get_enabled_library_variables` (from line 599) — accept `queries`**

Schema — add alongside the existing `query`:

```ts
queries: z.array(z.string()).min(1).max(20).optional().describe(
  "Batch form: filter on several variable-name substrings in one call. Returns one labelled result block per term. Use instead of repeated single-query calls."
),
```

Handler — the plugin command is already a single round trip per call, so batching happens server-side over one plugin response. Fetch **once with no query**, then filter in the server:

```ts
async ({ collectionKey, query, queries }: any) => {
  const terms: string[] = queries?.length ? queries : query ? [query] : [];
  try {
    // one plugin round trip regardless of term count
    const result: any = await sendCommandToFigma("get_enabled_library_variables", { collectionKey });
    if (terms.length <= 1) {
      // preserve today's shape exactly for the 0- and 1-term cases
      const filtered = terms.length === 1 ? filterVariables(result, terms[0]) : result;
      return { content: [{ type: "text", text: JSON.stringify(filtered) }] };
    }
    const byTerm = Object.fromEntries(terms.map((t) => [t, filterVariables(result, t)]));
    return { content: [{ type: "text", text: JSON.stringify({ queries: byTerm }) }] };
  } catch (error) { /* existing catch, unchanged */ }
}
```

`filterVariables(result, term)` applies the same case-insensitive name match the plugin currently does for `query`. Confirm the plugin-side filter in `src/figma_plugin/src/commands/styles.js` (or wherever `get_enabled_library_variables` is registered) before writing it, so server-side and plugin-side matching stay identical — if they diverge, a `query` and a one-element `queries` would return different results.

**Note on [BUG-029]**: this tool returned 2 collections then 14 for the same file in one session. Batching does not fix that and may *mask* it by making the unstable read less frequent. Do not close [BUG-029] off the back of this change.
