# Fix: [BUG-048] Assert a BOOLEAN component property keeps the `defaultValue` it was created with

**Pattern**: `assertion`
**Priority**: P1
**Estimated savings**: ~2 calls per occurrence (detect + repair); removes one class of component that ships rendering a state it should not

## Problem

`componentProperties`' `add` action (`src/figma_plugin/src/commands/components.js:417-435`) does:

```js
const fullName = node.addComponentProperty(op.name, op.type, op.defaultValue, options);
// … then, if op.targetNodeId:
refs[targetField] = fullName;
targetNode.componentPropertyReferences = refs;
```

For a BOOLEAN, `targetField` is `visible`. Session 63 ran this exact sequence by hand across 39
components and found the created default did not survive the bind:

```
{ name: "Accordion Item",     before: true,  after: false, ringsStillVisible: 0 }   // default flipped to true
{ name: "Alert Dialog Popup", before: false, after: false, ringsStillVisible: 1 }   // default held, ring left visible
```

Both ship the same defect — a component whose focus ring renders by default. The handler *returns*
`componentPropertyDefinitions` at `components.js:485`, so the wrong value is in the response, but
nothing compares it to what the caller asked for and nothing warns.

The underlying Figma mechanism is not isolated (see the tracker entry's named test). This fix does
not depend on it: it asserts the caller's stated intent and repairs a divergence.

## Changes

### File: `src/figma_plugin/src/commands/components.js` — the `add` branch

After the auto-bind block (`components.js:420-435`), before `results.push(addResult)`, re-read the
definition and re-assert the requested default when it diverged. Only for `add` operations that
actually bound a target — an unbound `add` has nothing to sync from.

```js
        // BUG-048 — binding a BOOLEAN to a layer's `visible` can leave the
        // property's defaultValue different from the one just requested (Figma
        // syncs it against the bound layer). The response would otherwise carry
        // the wrong default with no warning, and the component ships rendering
        // a state the caller asked to default off. Assert and repair.
        if (op.targetNodeId && addResult.boundTo) {
          const defsAfter = node.componentPropertyDefinitions || {};
          const defAfter = defsAfter[fullName];
          if (defAfter && defAfter.defaultValue !== op.defaultValue) {
            addResult.defaultDrifted = defAfter.defaultValue;
            try {
              node.editComponentProperty(fullName, { defaultValue: op.defaultValue });
              const recheck = node.componentPropertyDefinitions[fullName];
              addResult.defaultRestored = !!recheck && recheck.defaultValue === op.defaultValue;
            } catch (fixErr) {
              addResult.defaultRestoreError = fixErr.message || String(fixErr);
            }
          }
        }
```

Notes for the implementer:

- Use `!==` on the raw value, not a truthiness test — `false` is the value that matters here.
- Do **not** throw when the repair fails. The property and the binding both landed; the caller needs
  the result plus the divergence, not a rollback. `defaultRestoreError` carries it.
- The same drift is possible via the `bind` action (`components.js:453-472`), which binds an
  *existing* property. There the caller passed no `defaultValue`, so there is nothing to assert
  against — leave `bind` alone rather than inventing an expected value.

### File: `src/figmagent_mcp/tools/components.ts` — `component_properties` description

Add one sentence to the `add` bullet (`components.ts:166`), after the auto-bind sentence:

> Binding a BOOLEAN to `visible` can make Figma re-sync the property's default from the bound layer;
> the result reports `defaultDrifted`/`defaultRestored` when that happened and the requested
> `defaultValue` was re-asserted.
